## 1. 系统架构概述

One-API是一个大模型API聚合平台，提供统一的API接口，支持多个AI服务提供商的集成管理。系统采用分层架构设计，包含用户管理、令牌管理、渠道管理、日志记录、计费系统等核心模块。

### 1.1 技术栈
- **后端框架**: Go + Gin
- **数据库**: MySQL + GORM
- **缓存**: Redis
- **消息队列**: Redis Pub/Sub
- **API协议**: RESTful + OpenAI兼容

### 1.2 核心模块
```
┌─────────────────────────────────────────────┐
│                 请求层                        │
│  - HTTP请求处理                              │
│  - 中间件处理(认证、限流、CORS)              │
└─────────────────────────────────────────────┘
┌─────────────────────────────────────────────┐
│                 业务层                        │
│  - 令牌验证                                  │
│  - 渠道选择                                  │
│  - 配额管理                                  │
│  - 请求转发                                  │
└─────────────────────────────────────────────┘
┌─────────────────────────────────────────────┐
│                 数据层                        │
│  - 用户管理                                  │
│  - 令牌管理                                  │
│  - 渠道管理                                  │
│  - 日志记录                                  │
└─────────────────────────────────────────────┘
```

## 2. 用户管理核心逻辑

### 2.1 用户模型 (`model/user.go`)

#### 2.1.1 数据结构
```go
type User struct {
    Id               int    `json:"id" gorm:"primaryKey"`
    Username         string `json:"username" gorm:"unique;index"`
    Password         string `json:"password"`
    DisplayName      string `json:"display_name"`
    Role             int    `json:"role" gorm:"default:1"` // 1普通用户,10管理员,100根用户
    Status           int    `json:"status" gorm:"default:1"` // 1启用,2禁用
    Group            string `json:"group" gorm:"default:default"`
    Quota            int64  `json:"quota" gorm:"default:0"`
    UsedQuota        int64  `json:"used_quota" gorm:"default:0"`
    RequestCount     int    `json:"request_count" gorm:"default:0"`
    AccessToken      string `json:"access_token"`
    CreatedAt        int64  `json:"created_at"`
    UpdatedAt        int64  `json:"updated_at"`
}
```

#### 2.1.2 核心方法
- `ValidateAndFill()`: 验证用户凭据并填充用户信息
- `IncreaseUserQuota()`: 增加用户配额
- `UpdateUserUsedQuotaAndRequestCount()`: 更新用户使用统计
- `DeleteUser()`: 软删除用户
- `IsAdmin()`: 判断是否为管理员

### 2.2 用户认证流程
```
1. 用户登录 → 验证用户名密码 → 生成访问令牌
2. API调用 → 验证访问令牌 → 检查用户状态 → 检查配额
3. 权限检查 → 根据用户角色判断操作权限
```

## 3. 令牌管理核心逻辑

### 3.1 令牌模型 (`model/token.go`)

#### 3.1.1 数据结构
```go
type Token struct {
    Id           int    `json:"id" gorm:"primaryKey"`
    UserId       int    `json:"user_id" gorm:"index"`
    Key          string `json:"key" gorm:"type:varchar(255);uniqueIndex"`
    Name         string `json:"name"`
    Status       int    `json:"status" gorm:"default:1"` // 1启用,2禁用,3已过期
    CreatedAt    int64  `json:"created_at"`
    AccessedAt   int64  `json:"accessed_at"`
    ExpiredAt    int64  `json:"expired_at" gorm:"default:-1"`
    RemainQuota  int64  `json:"remain_quota" gorm:"default:-1"`
    Unlimited    bool   `json:"unlimited" gorm:"default:false"`
    Models       string `json:"models"` // 可用模型列表，逗号分隔
    Subnet       string `json:"subnet"` // 允许的IP段
}
```

#### 3.1.2 核心方法
- `ValidateUserToken()`: 验证用户令牌有效性
- `PreConsumeTokenQuota()`: 预消费令牌配额
- `PostConsumeTokenQuota()`: 后消费令牌配额
- `GetTokenByKey()`: 根据令牌Key获取令牌信息
- `UpdateTokenStatus()`: 更新令牌状态

### 3.3 令牌验证流程
```
1. 从请求头提取令牌
2. 验证令牌是否存在且有效
3. 检查令牌是否过期
4. 检查IP地址是否在允许范围内
5. 检查模型是否在允许列表中
6. 检查配额是否充足
```

## 4. 渠道管理核心逻辑

### 4.1 渠道模型 (`model/channel.go`)

#### 4.1.1 数据结构
```go
type Channel struct {
    Id               int    `json:"id" gorm:"primaryKey"`
    Type             int    `json:"type" gorm:"default:0"` // 渠道类型
    Key              string `json:"key" gorm:"type:varchar(255)"`
    Name             string `json:"name"`
    Status           int    `json:"status" gorm:"default:1"` // 1启用,2禁用,3已删除
    Weight           int    `json:"weight" gorm:"default:0"`
    CreatedAt        int64  `json:"created_at"`
    TestAt           int64  `json:"test_at"`
    ResponseAt       int64  `json:"response_at"`
    BalanceUpdatedAt int64  `json:"balance_updated_at"`
    Balance          float64 `json:"balance" gorm:"default:0"`
    Models           string `json:"models"` // 支持的模型列表
    Group            string `json:"group" gorm:"default:default"`
    UsedQuota        int64  `json:"used_quota" gorm:"default:0"`
    ModelMapping     string `json:"model_mapping"` // 模型映射关系
}
```

#### 4.1.2 渠道类型定义
```go
const (
    ChannelTypeOpenAI = iota
    ChannelTypeAnthropic
    ChannelTypeBaidu
    ChannelTypeXunfei
    ChannelTypeAli
    ChannelTypeZhipu
    ChannelTypeXunfei
    ChannelTypeAIProxyLibrary
    ChannelTypeTencent
    ChannelTypeGemini
    ChannelTypeMoonshot
    ChannelTypeBaichuan
)
```

### 4.2 渠道选择逻辑

#### 4.2.1 选择策略
```
1. 根据用户组筛选渠道
2. 根据模型需求筛选渠道
3. 根据渠道权重排序
4. 选择响应时间最短的渠道
5. 检查渠道余额是否充足
```

#### 4.2.2 渠道负载均衡
- **权重负载均衡**: 根据渠道权重分配请求
- **响应时间优化**: 优先选择响应时间短的渠道
- **余额检查**: 自动跳过余额不足的渠道
- **可用性测试**: 定期测试渠道可用性

### 4.3 渠道监控机制
- **自动测试**: 定时测试所有渠道可用性
- **响应时间记录**: 记录每个渠道的响应时间
- **余额监控**: 监控渠道余额变化
- **异常处理**: 自动禁用异常渠道

## 6. 配额管理核心逻辑

### 6.1 配额计算机制

#### 6.1.1 计费公式
```go
// 基础费用计算
actualQuota = promptTokens * ratio + completionTokens * ratio * completionRatio

// 分组系数
finalQuota = actualQuota * userGroupRatio * channelRatio
```

#### 6.1.2 模型定价表
- **基础模型**: 不同模型有不同的基础定价
- **分组系数**: 不同用户组有不同的价格系数
- **渠道系数**: 不同渠道有不同的成本系数

### 6.2 配额管理流程

#### 6.2.1 预消费机制
```
1. 请求前 → 计算预估配额
2. 检查用户配额是否充足
3. 预扣除配额（锁定配额）
4. 请求处理 → 计算实际配额
5. 调整预扣配额 → 多退少补
```

#### 6.2.2 配额回滚机制
- **请求失败**: 返还预扣配额
- **部分失败**: 按实际使用量计费
- **系统异常**: 自动回滚配额

## 7. 缓存机制核心逻辑

### 7.1 缓存架构

#### 7.1.1 多级缓存
```
┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│  本地缓存   │───►│  Redis缓存  │───►│  数据库    │
│  (热点数据) │    │  (共享数据) │    │  (源数据)  │
└─────────────┘    └─────────────┘    └─────────────┘
```

### 7.2 缓存内容

#### 7.2.1 用户相关缓存
- `user_quota:{user_id}`: 用户配额缓存
- `user_status:{user_id}`: 用户状态缓存
- `user_group:{user_id}`: 用户分组缓存

#### 7.2.2 令牌相关缓存
- `token:{token_key}`: 令牌信息缓存
- `token_quota:{token_id}`: 令牌配额缓存

#### 7.2.3 渠道相关缓存
- `channels:{group}:{model}`: 可用渠道列表
- `channel_balance:{channel_id}`: 渠道余额缓存
- `channel_status:{channel_id}`: 渠道状态缓存

### 7.3 缓存更新策略
- **TTL过期**: 设置合理的过期时间
- **主动更新**: 数据变更时主动更新缓存
- **延迟加载**: 缓存未命中时从数据库加载

## 8. 请求处理完整流程

### 8.1 文本请求处理流程

```
请求到达
    ↓
中间件处理
    ↓
令牌验证
    ↓
用户权限检查
    ↓
配额检查
    ↓
渠道选择
    ↓
模型映射
    ↓
请求转发
    ↓
响应处理
    ↓
配额扣减
    ↓
日志记录
    ↓
返回响应
```

### 8.2 错误处理机制

#### 8.2.1 错误分类
- **认证错误**: 401未授权、403禁止访问
- **配额错误**: 402配额不足
- **渠道错误**: 503服务不可用、504超时
- **参数错误**: 400参数错误
- **系统错误**: 500内部错误

#### 8.2.2 重试机制
- **自动重试**: 对特定错误码自动重试
- **渠道切换**: 失败时切换到备用渠道
- **指数退避**: 重试间隔逐渐增大

## 9. 监控与告警核心逻辑

### 9.1 监控指标

#### 9.1.1 业务指标
- **请求量**: 按用户、渠道、模型统计
- **成功率**: 整体成功率和各渠道成功率
- **响应时间**: 平均响应时间和P95/P99响应时间
- **配额使用**: 用户配额使用趋势

#### 9.1.2 系统指标
- **渠道状态**: 各渠道可用性监控
- **余额监控**: 渠道余额实时更新
- **错误统计**: 错误类型和频率统计

### 9.2 告警机制
- **渠道异常**: 渠道不可用或响应时间过长
- **配额告警**: 用户配额低于阈值
- **系统异常**: 系统错误率超过阈值
- **余额告警**: 渠道余额低于阈值
