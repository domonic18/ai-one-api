# One-API系统需求文档

## 1. 项目背景

### 1.1 系统架构概述

当前项目是一个多系统协作的大模型服务架构，包含以下核心系统：

- **课件制作平台**：面向教师用户的课件制作系统，维护用户、学校、学科组等基础信息
- **Dify系统**：工作流管理平台，配置不同工作流及其对应的模型参数
- **One-API系统**：大模型聚合平台，管理不同渠道（模型提供商）及其配额

### 1.2 当前系统链路

```
课件制作平台 → Dify系统 → One-API系统 → 大模型服务商
```

**具体流程**：
1. 课件制作平台与Dify系统通信，提供user_id（老师ID）
2. Dify系统配置One-API的API-KEY和BASE_URL
3. One-API系统配置多个大模型渠道（如deepseek、硅基流动等）
4. 通过模型名称自动匹配对应渠道，实现额度自动管理

### 1.3 当前配置示例

```bash
# Dify系统配置
BASE_URL=http://api.hk33smarter.com/v1
APIKEY=sk-xxx

# One-API系统配置
渠道1：deepseek渠道 → deepseek-chat模型
渠道2：硅基流动 → Qwen2.5-VL-72B模型
```

## 2. 核心需求

### 2.1 智能模型选择功能

#### 2.1.1 功能概述
实现智能选择模型功能，允许调用方通过特殊标识让One-API系统自动选择合适的模型。

#### 2.1.2 具体需求
1. **智能模型选择处理**：
   - 通过header中的"X-Smart-Model-Selection"字段控制是否启用智能模型选择
   - 当"X-Smart-Model-Selection"为"true"时，One-API系统根据header中的"X-User-ID"查询Redis缓存
   - 获取对应用户的模型选择名称和参数，替换请求中的模型名称和参数
   - 如果"X-Smart-Model-Selection"为"false"或不存在，则直接使用请求中的模型

#### 2.1.3 技术约束
- 通过Redis缓存存储用户模型配置信息
- 保持与现有API的兼容性
- 不影响正常模型请求的处理流程

### 2.2 多学校费用分别计算功能

#### 2.2.1 功能概述
实现按学校维度独立计费，支持多学校使用同一套系统但费用分别计算。

#### 2.2.2 具体需求
1. **费用分别计算**：
   - 每个学校使用大模型的费用独立计算
   - 支持学校A、B、C等不同学校的费用隔离
   - 每个学校可以购买不同的LLM模型提供商服务

2. **老师到学校映射**：
   - 通过teacher_id识别老师所属学校
   - 老师与学校的对应关系维护在课件制作平台
   - 在One-API中实现老师到学校的映射查询

3. **自动模型选择**：
   - 每个学校可以采买多个模型提供商
   - 在课件制作平台使用模型时，自动对学校采买的模型进行选择
   - 支持学校级别的模型偏好配置

4. **学校间隔离**：
   - 学校和学校之间完全独立
   - 不能相互影响大模型的使用
   - 配额和费用完全隔离

#### 2.2.3 技术约束
- Dify平台只能通过header提供user_id，无学校信息
- 不能在One-API中为每个老师创建账号（用户量大）
- 需要保持One-API的高性能特性
- 尽量不改动课件制作平台和Dify的业务逻辑

### 2.3 学科组级别费用管理

#### 2.3.1 功能概述
在学校级别基础上，进一步细化到学科组级别的费用管理和模型选择。

#### 2.3.2 具体需求
1. **学科组费用分离**：
   - 每个学科组的大模型使用费用独立计算
   - 支持学校内不同学科组的费用隔离

2. **学科组模型配置**：
   - 每个学科组可配置默认使用的模型
   - 支持学科组级别的模型偏好设置
   - 例如：数学组使用deepseek，语文组使用Qwen

3. **用户层级管理**：
   - 学校 → 学科组 → 老师的三级管理体系
   - 支持按学科组维度进行费用计算

#### 2.3.3 技术约束
- 需要扩展现有的用户组映射机制
- 支持学科组级别的渠道和配额配置
- 保持与学校级别管理的兼容性

### 2.4 数据同步与缓存机制

#### 2.4.1 功能概述
实现课件制作平台与One-API系统之间的数据同步，确保用户和组织信息的准确性。

#### 2.4.2 具体需求
1. **数据同步策略**：
   - 课件制作平台作为主数据源
   - One-API通过API调用获取必要数据
   - 支持定时同步和事件触发同步

2. **缓存机制**：
   - 使用Redis缓存提升查询性能
   - 支持多级缓存策略
   - 实现缓存失效和更新机制

3. **API接口设计**：
   - 课件制作平台提供数据查询API
   - 支持学校、学科组、老师信息的查询
   - 支持用户模型配置的查询

#### 2.4.3 技术约束
- 避免在One-API中重复维护课件平台已有的数据(特别是不要在One-API系统中再维护学校、学科组、老师的数据库表信息)
- 确保数据一致性和实时性
- 最小化对课件制作平台的影响

## 3. 非功能性需求

### 3.1 性能需求
1. **响应时间**：模型选择逻辑不应显著增加请求响应时间
2. **缓存命中率**：用户映射查询的缓存命中率应达到95%以上
3. **并发处理**：支持高并发请求处理
4. **系统稳定性**：保持原有系统的稳定性和可靠性

### 3.2 兼容性需求
1. **API兼容性**：保持与现有OpenAI兼容API的完全兼容
2. **系统兼容性**：不影响课件制作平台和Dify系统的正常使用
3. **数据兼容性**：保持现有数据库结构的兼容性

### 3.3 可维护性需求
1. **低耦合设计**：新功能与现有系统低耦合
2. **可扩展性**：支持未来功能扩展
3. **监控告警**：提供完善的监控和告警机制
4. **日志记录**：支持详细的日志记录和统计分析

### 3.4 安全性需求
1. **数据安全**：确保用户和组织信息的安全性
2. **访问控制**：实现适当的访问控制机制
3. **审计日志**：记录关键操作的审计日志

## 4. 系统约束

### 4.1 技术约束
1. **最小代码改动**：尽量避免大规模修改开源项目代码
2. **职责明确性**：各系统职责边界清晰，避免功能重叠
3. **数据维护唯一性**：避免在One-API中重复维护课件平台已有的数据
4. **性能优先**：保持请求链路的高性能，减少延迟

### 4.2 业务约束
1. **用户规模**：支持大量老师用户（不适合为每个老师创建账号）
2. **组织复杂度**：支持多学校、多学科组的复杂组织架构
3. **模型多样性**：支持多种大模型提供商和模型类型
4. **费用管理**：支持精细化的费用管理和计费

### 4.3 集成约束
1. **Dify集成**：Dify系统只能通过header提供user_id
2. **课件平台集成**：课件制作平台专注于课件制作，模型管理对其透明
3. **API限制**：需要遵循现有的API设计模式和规范
