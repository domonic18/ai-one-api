## 1. 项目背景

### 1.1 系统架构概述

当前项目是一个多系统协作的大模型服务架构，包含以下核心系统：

- **课件制作平台**：面向教师用户的课件制作系统，维护用户、学校、学科组等基础信息
- **Dify系统**：工作流管理平台，配置不同工作流及其对应的模型参数
- **One-API系统**：大模型聚合平台，管理不同渠道（模型提供商）及其配额

### 1.2 当前系统链路

```
课件制作平台 → Dify系统 → One-API系统 → 大模型服务商
```

**具体流程**：
1. 课件制作平台与Dify系统通信，提供user_id（老师ID）
2. Dify系统配置One-API的API-KEY和BASE_URL
3. One-API系统配置多个大模型渠道（如deepseek、硅基流动等）
4. 通过模型名称自动匹配对应渠道，实现额度自动管理

### 1.3 当前配置示例

```bash
# Dify系统配置
BASE_URL=http://api.hk33smarter.com/v1
APIKEY=sk-xxx

# One-API系统配置
渠道1：deepseek渠道 → deepseek-chat模型
渠道2：硅基流动 → Qwen2.5-VL-72B模型
```

## 2. 核心需求

### 2.1 智能模型选择功能

#### 2.1.1 功能概述
实现智能选择模型功能，允许调用方通过特殊标识让One-API系统自动选择合适的模型。

#### 2.1.2 具体需求
1. **智能模型选择处理**：
   - 通过header中的"X-Smart-Model-Selection"字段控制是否启用智能模型选择
   - 当"X-Smart-Model-Selection"为"true"时，One-API系统根据header中的"X-User-ID"查询用户偏好
   - 获取对应用户的模型选择名称和参数，替换请求中的模型名称和参数
   - 如果"X-Smart-Model-Selection"为"false"或不存在，则直接使用请求中的模型

#### 2.1.3 技术约束
- 通过Redis缓存存储用户模型配置信息
- 保持与现有API的兼容性
- 不影响正常模型请求的处理流程

#### 2.1.4 用户故事
- **US-001**: 作为Dify系统管理员，我希望通过设置"X-Smart-Model-Selection"为"true"来启用智能模型选择，这样系统可以自动为不同用户选择合适的模型。
- **US-002**: 作为老师用户，我希望系统能够根据我的偏好自动选择模型，而不需要每次都手动指定模型名称。

### 2.2 多学校费用分别计算功能

#### 2.2.1 功能概述
实现按学校维度独立计费，支持多学校使用同一套系统但费用分别计算。

#### 2.2.2 具体需求
1. **费用分别计算**：
   - 每个学校使用大模型的费用独立计算
   - 支持学校A、B、C等不同学校的费用隔离
   - 每个学校可以购买不同的LLM模型提供商服务

2. **老师到学校映射**：
   - 通过teacher_id识别老师所属学校
   - 老师与学校的对应关系维护在课件制作平台
   - 在One-API中实现老师到学校的映射查询

3. **自动模型选择**：
   - 每个学校可以采买多个模型提供商
   - 在课件制作平台使用模型时，自动对学校采买的模型进行选择
   - 支持学校级别的模型偏好配置

4. **学校间隔离**：
   - 学校和学校之间完全独立
   - 不能相互影响大模型的使用
   - 配额和费用完全隔离

#### 2.2.3 技术约束
- Dify平台只能通过header提供user_id，无学校信息
- 不能在One-API中为每个老师创建账号（用户量大）
- 需要保持One-API的高性能特性
- 尽量不改动课件制作平台和Dify的业务逻辑

#### 2.2.4 用户故事
- **US-003**: 作为学校A的管理员，我希望学校A的大模型使用费用独立计算，不会与学校B的费用混在一起。
- **US-004**: 作为学校A的老师，我希望使用学校A购买的模型服务，而不会使用到学校B的模型资源。

### 2.3 学校API-KEY配置管理

#### 2.3.1 功能概述
实现学校级别的模型提供商API-KEY配置管理，支持每个学校独立配置和管理自己的模型服务，同时提供默认分组支持确保学校在未配置时也能正常使用模型服务。

#### 2.3.2 具体需求
1. **学校模型服务配置**：
   - 每个学校可以配置多个模型提供商的API-KEY
   - 支持学校A配置Deepseek、Qwen、智谱等多个模型服务
   - 学校B配置的API-KEY与学校A完全独立

2. **模型服务隔离**：
   - 学校A的老师只能使用学校A配置的模型服务
   - 学校B的老师只能使用学校B配置的模型服务
   - 不同学校的相同模型使用不同的API-KEY

3. **模型服务验证**：
   - 学校未配置的模型服务无法使用
   - 系统自动验证模型服务的可用性
   - 提供模型服务配置状态监控

4. **默认分组支持**：
   - 学校未配置模型服务时，可分配默认分组
   - 管理员可为学校配置默认模型分组
   - 默认分组提供基础模型服务支持
   - 支持从默认分组平滑切换到独立配置

5. **配置流程管理**：
   - 新学校初始使用默认分组模型服务
   - 支持管理员为学校分配默认分组
   - 学校可随时配置独立API-KEY并切换
   - 配置切换过程不影响正常使用

#### 2.3.3 技术约束
- API-KEY配置需要加密存储
- 支持API-KEY的定期验证和更新
- 提供API-KEY使用情况的监控和统计
- 默认分组配置需要支持动态切换

#### 2.3.4 用户故事
- **US-005**: 作为学校A的管理员，我希望为学校A配置Deepseek的API-KEY，这样学校A的老师就可以使用Deepseek模型服务。
- **US-006**: 作为学校A的管理员，我希望为学校A配置Qwen的API-KEY，这样学校A的老师就可以同时使用Deepseek和Qwen两种模型服务。
- **US-007**: 作为学校B的管理员，我希望为学校B配置自己的Deepseek API-KEY，这样学校B的老师使用Deepseek时不会与学校A的API-KEY混用。
- **US-008**: 作为学校C的管理员，我希望在没有购买模型服务的情况下，系统管理员能为学校C分配默认分组，让学校C的老师也能使用基础模型服务。
- **US-016**: 作为系统管理员，我希望为新加入的学校D分配默认分组，确保学校D的老师能够立即使用模型服务，而不需要等待API-KEY配置完成。
- **US-017**: 作为学校E的管理员，我希望在配置好独立的API-KEY后，能够从默认分组平滑切换到独立配置，切换过程中不影响老师的正常使用。

### 2.4 学科组级别费用管理

#### 2.4.1 功能概述
在学校级别基础上，进一步细化到学科组级别的费用管理和模型选择。

#### 2.4.2 具体需求
1. **学科组费用分离**：
   - 每个学科组的大模型使用费用独立计算
   - 支持学校内不同学科组的费用隔离

2. **学科组模型配置**：
   - 每个学科组可配置默认使用的模型
   - 支持学科组级别的模型偏好设置
   - 例如：数学组使用GPT4.1，语文组使用Gemini2.5Pro

3. **用户层级管理**：
   - 学校 → 学科组 → 老师的三级管理体系
   - 支持按学科组维度进行费用计算

4. **模型选择灵活性**：
   - 学科组老师默认使用学科组配置的模型
   - 老师可在学校已配置的模型范围内自由选择
   - 个人模型选择不影响费用统计准确性

5. **默认学科组支持**：
   - 学校未设立学科组时，系统提供默认学科组
   - 默认学科组使用学校配置的默认模型
   - 支持后续学科组的动态创建和配置

#### 2.4.3 技术约束
- 需要扩展现有的用户组映射机制
- 支持学科组级别的渠道和配额配置
- 保持与学校级别管理的兼容性

#### 2.4.4 用户故事
- **US-009**: 作为学校A的数学组组长，我希望数学组默认使用GPT4.1模型，这样数学组的老师在使用模型时会自动选择GPT4.1。
- **US-010**: 作为学校A的语文组组长，我希望语文组默认使用Gemini2.5Pro模型，这样语文组的老师在使用模型时会自动选择Gemini2.5Pro。
- **US-011**: 作为数学组的老师，我希望在需要时能够切换到学校A已配置的其他模型（如Qwen），而不局限于数学组的默认模型。
- **US-012**: 作为系统管理员，我希望为没有设立学科组的学校提供默认学科组，确保这些学校的老师也能正常使用模型服务。
- **US-013**: 作为财务管理员，我希望能够按学科组维度统计费用，即使老师个人更换了模型，费用统计也要准确反映实际使用情况。

### 2.6 费用报表管理

#### 2.6.1 功能概述
实现多维度、多层次的费用报表功能，支持学校、学科组、老师级别的费用统计和查询，提供灵活的报表生成和查看功能。

#### 2.6.2 具体需求
1. **学校独立费用报表**：
   - 每个学校生成独立的费用报表
   - 报表包含学校总体费用统计
   - 支持按模型类型、使用量、费用等维度统计
   - 学校间费用数据完全隔离

2. **多层级费用统计**：
   - 学校级别：总体费用和使用情况
   - 学科组级别：各学科组的费用统计
   - 老师级别：每个老师的模型使用量和费用
   - 支持层级间的费用汇总和明细查看

3. **时间维度查询**：
   - 支持按年、月、周、天的时间维度查询
   - 提供时间范围选择器
   - 支持同比、环比分析
   - 支持自定义时间区间查询

4. **筛选和过滤功能**：
   - 按学科组名称筛选
   - 按老师姓名筛选
   - 按模型类型筛选
   - 按费用范围筛选
   - 支持多条件组合筛选

5. **权限控制**：
   - 学校只能查看自己的费用报表
   - 学校间无法查看各自的费用情况
   - 管理员可以查看所有学校的费用情况
   - 支持不同角色的报表访问权限

6. **报表导出功能**：
   - 支持Excel、PDF格式导出
   - 支持自定义报表模板
   - 支持定时报表生成和发送
   - 提供报表订阅功能

#### 2.6.3 技术约束
- 报表数据需要实时计算和缓存
- 支持大数据量的报表生成
- 提供报表数据的备份和恢复
- 确保报表数据的准确性和一致性

#### 2.6.4 用户故事
- **US-018**: 作为学校A的财务管理员，我希望能够查看学校A的独立费用报表，了解学校在模型服务上的总支出。
- **US-019**: 作为数学组组长，我希望能够查看数学组的费用统计，了解数学组在模型使用上的费用情况。
- **US-020**: 作为老师，我希望能够查看自己的模型使用量和费用，了解个人在模型服务上的使用情况。
- **US-021**: 作为系统管理员，我希望能够查看所有学校的费用报表，进行整体费用分析和监控。
- **US-022**: 作为学校B的管理员，我希望能够按月份查看费用报表，进行月度费用分析和预算规划。
- **US-023**: 作为学科组组长，我希望能够按老师姓名筛选费用报表，了解组内各老师的模型使用情况。

### 2.5 数据同步与缓存机制

#### 2.5.1 功能概述
实现课件制作平台与One-API系统之间的数据同步，确保用户和组织信息的准确性。

#### 2.5.2 具体需求
1. **数据同步策略**：
   - 课件制作平台作为主数据源
   - One-API通过API调用获取必要数据
   - 支持定时同步和事件触发同步

2. **缓存机制**：
   - 使用Redis缓存提升查询性能
   - 支持多级缓存策略
   - 实现缓存失效和更新机制

3. **API接口设计**：
   - 课件制作平台提供数据查询API
   - 支持学校、学科组、老师信息的查询
   - 支持用户模型配置的查询

4. **费用数据同步**：
   - 实时同步模型使用费用数据
   - 支持费用数据的增量更新
   - 确保费用统计的实时性和准确性

#### 2.5.3 技术约束
- 避免在One-API中重复维护课件平台已有的数据(特别是不要在One-API系统中再维护学校、学科组、老师的数据库表信息)
- 确保数据一致性和实时性
- 最小化对课件制作平台的影响

#### 2.5.4 用户故事
- **US-014**: 作为系统管理员，我希望课件制作平台的数据变更能够及时同步到One-API系统，确保模型选择逻辑的准确性。
- **US-015**: 作为老师用户，我希望系统能够快速响应我的模型选择请求，通过缓存机制减少查询延迟。

## 3. 非功能性需求

### 3.1 性能需求
1. **响应时间**：模型选择逻辑不应显著增加请求响应时间
2. **缓存命中率**：用户映射查询的缓存命中率应达到95%以上
3. **并发处理**：支持高并发请求处理
4. **系统稳定性**：保持原有系统的稳定性和可靠性

### 3.2 兼容性需求
1. **API兼容性**：保持与现有OpenAI兼容API的完全兼容
2. **系统兼容性**：不影响课件制作平台和Dify系统的正常使用
3. **数据兼容性**：保持现有数据库结构的兼容性

### 3.3 可维护性需求
1. **低耦合设计**：新功能与现有系统低耦合
2. **可扩展性**：支持未来功能扩展
3. **监控告警**：提供完善的监控和告警机制
4. **日志记录**：支持详细的日志记录和统计分析

### 3.4 安全性需求
1. **数据安全**：确保用户和组织信息的安全性
2. **访问控制**：实现适当的访问控制机制
3. **审计日志**：记录关键操作的审计日志
4. **API-KEY安全**：API-KEY加密存储，定期轮换

## 4. 系统约束

### 4.1 技术约束
1. **最小代码改动**：尽量避免大规模修改开源项目代码
2. **职责明确性**：各系统职责边界清晰，避免功能重叠
3. **数据维护唯一性**：避免在One-API中重复维护课件平台已有的数据
4. **性能优先**：保持请求链路的高性能，减少延迟

### 4.2 业务约束
1. **用户规模**：支持大量老师用户（不适合为每个老师创建账号）
2. **组织复杂度**：支持多学校、多学科组的复杂组织架构
3. **模型多样性**：支持多种大模型提供商和模型类型
4. **费用管理**：支持精细化的费用管理和计费
5. **API-KEY管理**：支持学校级别的API-KEY独立配置和管理
6. **报表需求**：支持多维度、多层次的费用报表生成和查询
7. **默认分组支持**：确保学校在未配置时也能正常使用模型服务

### 4.3 集成约束
1. **Dify集成**：Dify系统只能通过header提供user_id
2. **课件平台集成**：课件制作平台专注于课件制作，模型管理对其透明
3. **API限制**：需要遵循现有的API设计模式和规范
4. **模型提供商集成**：支持多种模型提供商的API-KEY配置和管理
